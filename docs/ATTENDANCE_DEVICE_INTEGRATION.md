# خطة ربط الحضور والانصراف بجهاز بصمة ZKTeco

**الغرض:** هذه الوثيقة تحدد كل ما يجب تجهيزه خارج الكود لربط نظام ClickERP بجهاز بصمة ZKTeco
(الموديل المستهدف MB2000)، وما هو مطلوب من المورد، ومن مسؤول السيرفر، ومن مسؤول شبكة المكتب،
وإعدادات الجهاز نفسه، وخطوات الفحص والقبول.

**الجهات المعنية بكل قسم:**

| القسم | المسؤول |
|---|---|
| 1. متطلبات المورد | المورد + الإدارة |
| 2. إعدادات السيرفر والدومين | مسؤول الاستضافة / المطور |
| 3. شبكة المكتب | مسؤول الشبكة / فني المورد |
| 4. إعدادات الجهاز | فني المورد + موظف HR المسؤول |
| 5. تجهيز بيانات HR | قسم الموارد البشرية |
| 6. الفحص والقبول | HR + المطور |
| 7. ما سيُبنى في النظام | المطور (للاطلاع فقط) |

---

## ملخص طريقة الربط

يعمل الربط بطريقة **ADMS / Push** (بروتوكول iClock من ZKTeco):

- الجهاز هو الذي **يرسل** كل بصمة إلى السيرفر عبر HTTP فور حدوثها.
- السيرفر لا يتصل بالجهاز، لذلك **لا حاجة لفتح منافذ** في راوتر المكتب ولا لعنوان IP عام ثابت للمكتب.
- الجهاز يحتاج فقط إلى إنترنت ووصول إلى دومين النظام على المنفذ 80.
- في حال انقطاع الإنترنت يخزن الجهاز البصمات داخلياً (حتى 100,000 سجل) ويرسلها عند عودة الاتصال.

الطريقة البديلة (السحب عبر المنفذ 4370) غير مناسبة لأن السيرفر على الإنترنت والجهاز خلف راوتر المكتب.

## 1. متطلبات المورد (جهاز البصمة)

يُطلب من المورد تأكيد النقاط التالية **كتابياً قبل التوريد**:

| # | المطلوب | ملاحظة |
|---|---|---|
| 1 | الموديل MB2000 (أو بديل من القائمة أدناه) | وجه + بصمة + بطاقة |
| 2 | الفيرموير **يدعم ADMS / Push SDK** | يظهر في قائمة الجهاز باسم `Cloud Server Setting` تحت `Comm.` |
| 3 | تزويدنا بـ **الرقم التسلسلي (Serial Number)** ورقم الفيرموير قبل التركيب | يلزم لتسجيل الجهاز في النظام مسبقاً |
| 4 | هل الفيرموير يدعم إرسال ADMS عبر **HTTPS**؟ | إن لم يدعم، سنستخدم HTTP على دومين فرعي مخصص |
| 5 | كابل شبكة RJ45 أو موديل بـ WiFi | الكابل أضمن |
| 6 | محول كهرباء أصلي 12V | مرفق عادة |
| 7 | كلمة مرور Super Admin الافتراضية وطريقة إعادة الضبط | تُسلَّم لموظف HR المسؤول |
| 8 | حضور فني المورد يوم التركيب لضبط الشبكة والسيرفر السحابي | حسب القسمين 3 و 4 |

**موديلات بديلة مقبولة** (كلها تعمل بنفس البروتوكول): MB20، MB460، K40 / K50 نسخة ADMS، F18، F22،
uFace 202 / 402 / 800، SpeedFace V5L، iClock 360 / 680.

**غير مقبول:** أجهزة Hikvision أو Suprema أو Anviz أو أي جهاز ZKTeco بدون خيار Cloud Server في القائمة.

## 2. إعدادات السيرفر والدومين

| # | الإعداد | التفاصيل |
|---|---|---|
| 1 | دومين فرعي للأجهزة | مثال: `adms.example.com` يشير إلى نفس سيرفر النظام (سجل A) |
| 2 | HTTP على المنفذ 80 | مسموح للمسارات `/iclock/*` فقط بدون تحويل إجباري إلى HTTPS |
| 3 | حجم الطلب | `client_max_body_size 10m` لاستقبال صور المستخدمين من الجهاز |
| 4 | Cloudflare (إن وجد) | الدومين الفرعي **DNS only** (سحابة رمادية)، أو قاعدة WAF تستثني `/iclock/*` من Bot Fight / Challenge |
| 5 | جدار السيرفر الناري | السماح بالوارد على المنفذ 80 (على الأقل من IP المكتب العام) |
| 6 | الوقت | ساعة السيرفر مضبوطة بـ NTP؛ توقيت التطبيق `Asia/Riyadh` (مضبوط بالفعل في `config/app.php`) |
| 7 | كرون | `schedule:run` كل دقيقة (موجود بالفعل، انظر `docs/CRON_JOBS.md`) |
| 8 | نسخة احتياطية | `mysqldump` قبل تشغيل migrations الجداول الجديدة |

### مثال إعداد nginx للدومين الفرعي

```nginx
server {
    listen 80;
    server_name adms.example.com;
    root /home/platinum/public_html/public;
    client_max_body_size 10m;

    # مسارات الجهاز فقط، أي مسار آخر يُحوَّل إلى الموقع الرئيسي
    location /iclock/ {
        try_files $uri /index.php?$query_string;
    }

    location ~ \.php$ {
        include fastcgi_params;
        fastcgi_pass unix:/run/php/php8.2-fpm.sock;
        fastcgi_param SCRIPT_FILENAME $realpath_root$fastcgi_script_name;
    }

    location / {
        return 301 https://example.com$request_uri;
    }
}
```

على استضافة cPanel: أنشئ Subdomain يشير إلى نفس مجلد `public_html`، وتأكد أن قاعدة إعادة التوجيه إلى
HTTPS في `.htaccess` تستثني `/iclock/`:

```apache
RewriteCond %{HTTPS} off
RewriteCond %{REQUEST_URI} !^/iclock/
RewriteRule ^ https://%{HTTP_HOST}%{REQUEST_URI} [L,R=301]
```

### فحص جاهزية السيرفر (قبل وصول الجهاز)

من أي جهاز على الإنترنت:

```bash
curl -i "http://adms.example.com/iclock/cdata?SN=TEST123&options=all"
```

المطلوب: رد HTTP (200 بعد نشر الكود، أو 404 من Laravel قبله). أي رد من Cloudflare بصفحة تحدي، أو
تحويل 301 إلى HTTPS، يعني أن الإعداد لم يكتمل.

## 3. شبكة المكتب

| # | المطلوب | التفاصيل |
|---|---|---|
| 1 | نقطة شبكة وكهرباء عند موقع التركيب | يفضل UPS؛ بطارية الجهاز الداخلية للانقطاع القصير فقط |
| 2 | عنوان IP للجهاز | ثابت، أو حجز DHCP بربط MAC الجهاز في الراوتر |
| 3 | Gateway و DNS | DNS صالح للإنترنت مثل `8.8.8.8` |
| 4 | إنترنت من شبكة الجهاز | وصول صادر إلى الدومين على المنفذ 80، بدون Captive Portal ولا Proxy |
| 5 | لا حاجة لفتح منافذ واردة | الجهاز هو المُرسِل |
| 6 | WiFi (إن استُخدم) | شبكة 2.4GHz فقط |

### فحص الشبكة من لابتوب على نفس الشبكة

```bash
ping adms.example.com
curl -i "http://adms.example.com/iclock/cdata?SN=TEST123&options=all"
```

إذا نجح هذا الفحص من اللابتوب فسينجح من الجهاز.

## 4. إعدادات الجهاز (MB2000)

الدخول إلى القائمة يتطلب Super Admin. أسماء القوائم قد تختلف قليلاً حسب نسخة الفيرموير.

### 4.1 الشبكة

| القائمة | الإعداد | القيمة |
|---|---|---|
| Comm. ← Ethernet | DHCP | Off مع IP ثابت (أو On مع حجز في الراوتر) |
| Comm. ← Ethernet | IP Address / Subnet Mask / Gateway | حسب شبكة المكتب |
| Comm. ← Ethernet | DNS | `8.8.8.8` |
| Comm. ← Ethernet | TCP COMM. Port | `4370` (يبقى كما هو) |
| Comm. ← Wireless Network | WiFi | فقط إن لم يوجد كابل |

### 4.2 الاتصال بالسيرفر (الأهم)

| القائمة | الإعداد | القيمة |
|---|---|---|
| Comm. ← Cloud Server Setting | Enable Domain Name | **On** |
| Comm. ← Cloud Server Setting | Server Address | `adms.example.com` (بدون `http://` وبدون `/`) |
| Comm. ← Cloud Server Setting | Server Port | `80` |
| Comm. ← Cloud Server Setting | Enable Proxy Server | **Off** |
| Comm. ← Cloud Server Setting | HTTPS | Off (إلا إن أكد المورد دعمه، وحينها `443` مع الدومين الرئيسي) |

بعد الحفظ **أعد تشغيل الجهاز**. ظهور أيقونة السحابة ثابتة أعلى الشاشة يعني نجاح الاتصال. إن كانت
متقطعة أو غير ظاهرة: راجع DNS، ثم المنفذ 80، ثم الدومين.

### 4.3 الوقت

| القائمة | الإعداد | القيمة |
|---|---|---|
| System ← Date Time | Time Zone | `UTC+03:00` |
| System ← Date Time | Date / Time | مطابق لساعة السيرفر (يمكن للنظام تصحيحها لاحقاً عبر ADMS) |
| System ← Date Time | 24-Hour Time | On |

### 4.4 سياسة الحضور

| القائمة | الإعداد | القيمة |
|---|---|---|
| System ← Attendance | Duplicate Punch Period | `1` دقيقة |
| System ← Attendance | Punch State Mode | **Off** (النظام يحدد الحضور بأول بصمة والانصراف بآخر بصمة في اليوم) |
| System ← Attendance | Attendance Log Alert | `1000` |
| System ← Attendance | Cyclic Delete ATT Data | `Disabled` |

### 4.5 المستخدمون

| القائمة | الإعداد | القيمة |
|---|---|---|
| User Mgt. ← New User | User ID | **نفس كود الموظف في ClickERP حرفياً** (أرقام فقط) |
| User Mgt. ← New User | Name | اسم الموظف |
| User Mgt. ← New User | Fingerprint | إصبعان على الأقل |
| User Mgt. ← New User | Face | تسجيل الوجه |
| User Mgt. ← New User | User Role | `Normal User` |
| User Mgt. | Super Admin | موظف HR مسؤول واحد + كلمة مرور، تُحفظ في مكان آمن |

تسجيل البصمة والوجه يتم **على الجهاز فعلياً فقط**. الأسماء وأرقام المستخدمين يمكن للنظام إرسالها
للجهاز لاحقاً، لكن الإدخال اليدوي أضمن في المرحلة الأولى.

### 4.6 معلومات تُسجَّل وتُسلَّم للمطور

| القائمة | المعلومة |
|---|---|
| System Info ← Device Info | Serial Number |
| System Info ← Device Info | Firmware Version |
| System Info ← Device Info | MAC Address |
| Comm. ← Ethernet | IP Address المضبوط |

### 4.7 تنبيهات

- إن كان الجهاز مستعملاً وعليه سجلات سابقة: صدّرها إلى USB من `Data Mgt.` ثم امسحها قبل الربط،
  لأن الجهاز سيرسل كل السجلات القديمة عند أول اتصال.
- لا تفعّل `Cloud Server Setting` قبل تسجيل الرقم التسلسلي في النظام، وإلا سيُرفض الجهاز.
- أقفل قائمة الجهاز بكلمة مرور Super Admin. بدونها لا يمكن تغيير عنوان السيرفر لاحقاً.

| # | المطلوب | السبب |

| 4 | ربط كل جهاز بفرع | للعمل مع وضع الفروع المتعددة |
| 5 | كل موظف مسجل على جهاز فرعه بنفس الكود | |

## 6. الفحص والقبول

| # | الخطوة | النتيجة المتوقعة |
|---|---|---|
| 1 | فحص curl من الإنترنت على `/iclock/cdata` | رد من Laravel بدون تحدي أو تحويل |
| 2 | تسجيل SN الجهاز واسمه وفرعه في شاشة الأجهزة | الجهاز يظهر بحالة "لم يتصل بعد" |
| 3 | ضبط Cloud Server Setting وإعادة التشغيل | أيقونة السحابة ثابتة، والجهاز يظهر "متصل" مع وقت آخر اتصال |
| 4 | بصمة تجريبية لموظف مسجل | تظهر خلال ثوانٍ في جدول البصمات الخام بنفس الكود والوقت |
| 5 | بصمة لموظف غير مسجل بالنظام | تُحفظ خام وتظهر في تقرير "أكواد غير مطابقة" |
| 6 | فصل الإنترنت، بصمتان، إعادة الإنترنت | البصمتان تصلان بعد عودة الاتصال بوقتهما الأصلي |
| 7 | اليوم التالي | مهمة التجميع أنشأت سجل حضور/انصراف لكل موظف وغرامة التأخير عند اللزوم |
| 8 | أسبوع تشغيل موازٍ مع شيت الإكسل | تطابق النتائج، ثم إيقاف الشيت |

## 7. ما سيُبنى في النظام (للاطلاع)

هذا القسم يوضح ما سيصل من جهة الكود حتى تكون الصورة كاملة، ولا يتطلب أي إجراء من المورد أو الشبكة.

1. **إعادة هيكلة** منطق رفع الشيت إلى خدمة تسجيل حضور موحدة مع منع التكرار ومعالجة الأكواد المفقودة.
2. **جدول أجهزة** (`hr_attendance_devices`): الرقم التسلسلي، الاسم، الفرع، آخر اتصال، الحالة.
3. **جدول بصمات خام** (`hr_attendance_punches`): الجهاز، الكود، الوقت، نوع التحقق، المصدر
   (جهاز / شيت / موقع جغرافي)، بمفتاح فريد يمنع التكرار.
4. **مسارات ADMS** بدون CSRF وبدون تسجيل دخول، مقيدة بالرقم التسلسلي المسجل:
   `/iclock/cdata`، `/iclock/getrequest`، `/iclock/devicecmd`.
5. **مهمة مجدولة** تجمع بصمات اليوم لكل موظف (أول بصمة حضور، آخر بصمة انصراف) وتكتب في
   `hr_employee_attendances` وتطبق منطق التأخير الحالي، بتوقيت قابل للضبط من إعدادات الأتمتة.
6. **شاشة أجهزة البصمة** في قسم HR بصلاحية جديدة، وتقرير أكواد غير مطابقة.
7. **صفحة تبصيم بالموقع الجغرافي** للموظفين الميدانيين (مرحلة لاحقة) تستخدم نفس جدول البصمات الخام.
8. **إعادة تصميم صفحة رفع الشيت** لتصبح "مصادر الحضور" بثلاثة تبويبات: شيت، أجهزة، موقع.
