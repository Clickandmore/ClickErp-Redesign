# حالة تنفيذ نظام الفروع

تاريخ التحديث: 2026-06-17

هذا الملف يلخص ما تم تنفيذه فعليا في نظام الفروع، وما تبقى تنفيذه بعد المرحلة الحالية.

---

## 1. ما تم تنفيذه

### 1.1 الأساس وإدارة الفروع

- تم إنشاء جدول الفروع `branches`.
- تم إضافة موديل `Branch`.
- تم تجهيز شاشة إدارة الفروع.
- تم ربط نظام الفروع بموديول `branches` داخل إعدادات Dev Super Admin.
- تم دعم تعطيل/تفعيل الفروع بحيث لا تؤثر على الشركات التي لا تستخدم الفروع.
- تم تجهيز صلاحيات الفروع الأساسية وربطها بمنظومة الصلاحيات الحالية.

### 1.2 ربط الموظفين بالفروع

- تم إضافة `branch_id` إلى جدول `admins`.
- تم إضافة علاقة الفرع داخل موديل `Admin`.
- تم دعم اختيار الفرع عند إنشاء/تعديل الموظف.
- تم دعم فلترة الموظفين حسب الفرع.
- الموظف المرتبط بفرع يمكن استخدام فرعه تلقائيا في إنشاء السجلات الجديدة.

### 1.3 ربط العملاء والطلبات والعقود والفواتير الأساسية

- تم إضافة `branch_id` إلى:
  - `users`
  - `orders`
  - `contracts`
  - `rental_contracts`
  - `invoices`
- تم عمل backfill للسجلات القديمة قدر الإمكان من الموظف/الطلب/العقد المرتبط.
- تم ربط الموديلات الأساسية بالفرع.
- تم دعم إسناد الفرع تلقائيا عند إنشاء السجلات الجديدة.

### 1.4 فلتر الفروع في الداشبورد

- تم إضافة فلتر الفروع في الداشبورد.
- الأدمن العام يستطيع رؤية كل الفروع أو اختيار فرع محدد.
- موظف الفرع يرى بيانات فرعه فقط.
- الفلتر يختفي أو لا يؤثر عند تعطيل موديول `branches`.
- تم تطبيق الفلترة على أهم إحصائيات الداشبورد الحالية.

### 1.5 المرحلة الثانية: ربط الجداول التشغيلية

تم إنشاء وتشغيل migration:

```text
2026_06_17_000001_add_branch_id_to_operational_tables
```

هذا الـ migration أضاف `branch_id` وعمل backfill للجداول التشغيلية التالية عند وجودها:

- `recruitment_requests`
- `complaints`
- `complaint_comments`
- `complaint_timelines`
- `complaint_feedbacks`
- `contract_payments`
- `contract_notes`
- `contract_status_logs`
- `sponsorship_transfers`
- `transfer_service_contracts`
- `musaned_transfers`
- `musaned_transfer_items`
- `ingaz_delegations`
- `rental_financial_adjustments`
- `rental_contract_invoices`
- `rental_contract_extensions`
- `maid_attachments`
- `client_attachments`
- `recruitment_contract_attachments`
- `maid_recruitment_procedures`
- `contract_external_office_dispatches`
- `recruitment_contract_refunds`
- `contract_return_requests`
- `financial_requests`
- `financial_request_attachments`
- `order_transfers`

### 1.6 إسناد الفرع تلقائيا في الموديلات

تم توسيع `App\Models\Concerns\AssignsBranch` بحيث يستطيع استنتاج الفرع من:

- الموظف الحالي.
- موظف محدد.
- العميل.
- الطلب.
- العقد.
- عقد التأجير.
- الفاتورة.
- الشكوى.
- العاملة.
- الطلب المالي.

وتم ربط موديلات تشغيلية كثيرة بهذا الـ trait حتى يتم تعبئة `branch_id` تلقائيا عند إنشاء السجلات الجديدة.

### 1.7 فلترة backend لبعض القوائم المهمة

تم إضافة فلترة backend بالفرع في الصفحات التالية:

- الشكاوى.
- تقييمات الشكاوى.
- طلبات نقل الكفالة.
- عقود نقل الخدمة.
- تفويضات إنجاز.
- تحويلات مساند.
- الطلبات المالية.
- طلبات إرجاع العقود.
- إرسالات المكتب الخارجي.

ملاحظة: بعض هذه الصفحات أصبحت تقبل `branch_id` في الخلفية، لكن قد لا تحتوي كل الواجهات على dropdown ظاهر لاختيار الفرع.

## 2. ما تم اختباره

- تم تشغيل migration المرحلة الثانية بنجاح.
- تم تشغيل فحص PHP syntax على الملفات المعدلة.
- تم تشغيل:

```bash
php artisan view:cache
```

ونجح بدون أخطاء.

- تم تشغيل:

```bash
git diff --check
```

ولا توجد أخطاء تنسيق مؤثرة، فقط تحذيرات line endings المعتادة على Windows.

## 3. المتبقي تنفيذه

### 3.1 استكمال عزل القوائم

المطلوب مراجعة باقي القوائم واحدة واحدة وتطبيق فلتر الفرع عليها عند الحاجة، خصوصا:

- أي شاشة DataTable لم تتم مراجعتها بعد.
- أي شاشة Ajax.
- أي شاشة تعرض بيانات تشغيلية مرتبطة بعقود أو عملاء أو فواتير.
- أي exports أو تقارير تصدر Excel/PDF.

الهدف:

- موظف الفرع لا يرى سجلات فرع آخر.
- الأدمن العام يرى كل السجلات أو يفلتر حسب فرع.
- عند تعطيل موديول `branches` لا يتم تطبيق أي فلترة.

### 3.2 منع الروابط المباشرة

الفلترة في القوائم وحدها لا تكفي.

المطلوب إضافة تحقق في صفحات:

- `show`
- `edit`
- `update`
- `destroy`
- أي actions حساسة مثل approve/process/pay/print

حتى لا يستطيع موظف فرع فتح سجل تابع لفرع آخر عبر URL مباشر.

### 3.3 إظهار فلتر الفرع في الواجهات

بعض الصفحات تم دعم فلتر الفرع فيها في backend، لكن الواجهة لا تعرض selector حتى الآن.

المطلوب:

- إضافة dropdown للفروع في الصفحات المهمة للأدمن العام.
- إخفاؤه عن موظف الفرع.
- إخفاؤه تماما عند تعطيل موديول `branches`.
- تمرير `branch_id` في Ajax/DataTables/روابط pagination.

### 3.4 مراجعة التقارير والتصدير

المطلوب التأكد من أن التقارير والتصدير يحترمان الفرع:

- تقارير العملاء.
- تقارير الطلبات.
- تقارير العقود.
- تقارير الفواتير.
- التقارير المالية.
- تقارير الإيواء أو التشغيل إن وجدت.

### 3.5 بناء تقارير الفروع

مرحلة تقارير الفروع لم تبدأ بعد.

المطلوب لاحقا:

- تقرير لكل فرع.
- مقارنة بين الفروع.
- أداء الموظفين حسب الفرع.
- الطلبات حسب الفرع.
- العقود حسب الفرع.
- الإيرادات والفواتير حسب الفرع.
- مؤشرات تشغيلية واضحة لكل فرع.

### 3.6 اختبار الصلاحيات وسيناريوهات الاستخدام

المطلوب اختبار السيناريوهات التالية:

- أدمن عام بدون فلتر يرى كل البيانات.
- أدمن عام يختار فرع محدد ويرى بياناته فقط.
- موظف فرع يرى فرعه فقط.
- موظف فرع لا يستطيع فتح رابط مباشر لسجل فرع آخر.
- تعطيل موديول `branches` يجعل النظام يعمل كشركة واحدة بدون فلترة.
- إنشاء سجل جديد من موظف فرع يربطه تلقائيا بفرعه.
- إنشاء سجل جديد من أدمن عام بدون اختيار فرع لا يكسر النظام.

---

## 4. ملاحظات مهمة

- لا يوجد جدول مستقل باسم `payments` في المشروع حسب المراجعة الحالية، والموجود فعليا هو `contract_payments` وقد تم ربطه بالفروع.
- `branch_id` ما زال nullable في الجداول الجديدة، وهذا مقصود حتى لا تنكسر السجلات القديمة أو الشركات التي لا تستخدم الفروع.
- لا يوجد Global Scope للفروع حتى الآن، وهذا مقصود لتقليل المخاطر.
- أي عزل جديد يجب أن يتم شاشة شاشة، مع اختبار DataTables وAjax والتصدير.

---

## 5. الترتيب المقترح للمرحلة القادمة

1. مراجعة كل صفحات القوائم المهمة وتحديد التي لا تطبق فلتر الفرع.
2. إضافة واجهة اختيار الفرع للأدمن العام في الصفحات التي تحتاجها.
3. إضافة منع الوصول المباشر في `show/edit/update/delete`.
4. مراجعة exports والتقارير.
5. بناء صفحة تقارير الفروع.
6. تنفيذ اختبار يدوي كامل بأدمن عام وموظف فرع.
