# خطة إدارة فروع الشركة في لوحة التحكم

هذا الملف هو المرجع التنفيذي لبناء نظام فروع الشركة داخل لوحة التحكم:

```text
http://127.0.0.1:8000/dashboard
```

الهدف ليس مجرد إضافة شاشة فروع، بل بناء طبقة تنظيمية تساعد على إدارة الموظفين والطلبات والعقود والتقارير حسب الفرع مع أقل تأثير ممكن على سير العمل الحالي.

---

## 1. الهدف

إضافة نظام لإدارة فروع الشركة بحيث يمكن:

- إنشاء وتعديل وتعطيل الفروع.
- ربط موظفي لوحة التحكم بفروع الشركة.
- عرض إحصائيات وتقارير كل فرع.
- تقييد رؤية البيانات حسب الفرع عند الحاجة.
- الحفاظ على عمل النظام الحالي بدون كسر الشاشات أو التقارير.
- تفعيل عزل البيانات تدريجيا بعد الاختبار.

---

## 2. المبادئ الحاكمة

### 2.1 لا نكسر السلوك الحالي

أي حقل جديد يجب أن يكون اختياريا في البداية، خصوصا `branch_id`.

لا يتم إجبار السجلات القديمة على فرع محدد قبل مراجعة البيانات.

### 2.2 لا نستخدم Global Scope في البداية

استخدام Global Scope لعزل الفروع من أول مرحلة خطر، لأنه قد يؤثر على:

- الداشبورد.
- التقارير.
- الفواتير.
- العقود.
- شاشات Ajax و DataTables.
- أوامر Artisan.

الأفضل استخدام خدمة مركزية للفلترة ثم تطبيقها تدريجيا في الشاشات المطلوبة.

### 2.3 الفروع ليست المكاتب الخارجية

يوجد في النظام مفهوم `recruitment_offices`، وهو مستخدم للمكاتب الخارجية ومكاتب الاستقدام المرتبطة بالسير الذاتية والعاملات.

لا نستخدم هذا الجدول كفروع للشركة.

الفروع الداخلية تحتاج جدولا مستقلا باسم `branches`.

### 2.4 التفعيل على مراحل

نبدأ بإدارة الفروع وربط الموظفين، ثم نضيف فلتر الداشبورد، ثم ربط السجلات الجديدة، ثم عزل القوائم والتقارير.

### 2.5 الفروع ميزة اختيارية حسب الشركة

النظام مستخدم على أكثر من شركة، وبعض الشركات قد لا يكون لديها فروع أصلا.

لذلك يجب ألا يكون وجود الفروع شرطا لتشغيل النظام.

يجب دعم وضعين:

```text
شركة بدون فروع: النظام يعمل كأنه شركة واحدة، بدون إظهار تعقيد الفروع للمستخدم.
شركة لديها فروع: يتم تفعيل إدارة الفروع والفلترة والعزل حسب السياسة المعتمدة.
```

هذا يعني أن كل إضافة خاصة بالفروع يجب أن تمر عبر إعداد أو حالة تشغيل واضحة، وليس افتراض أن كل شركة لديها فروع.

---

## 3. النطاق

### داخل النطاق

- جدول الفروع.
- شاشة إدارة الفروع.
- صلاحيات الفروع.
- ربط موظفي `admins` بالفروع.
- فلتر الفروع في الداشبورد.
- ربط السجلات التشغيلية الجديدة بالفرع.
- فلترة البيانات حسب الفرع في القوائم المهمة.
- تقارير أداء الفروع.

### خارج النطاق في المرحلة الأولى

- إعادة هيكلة كل النظام حول الفروع دفعة واحدة.
- تغيير جداول المكاتب الخارجية.
- تعديل كل التقارير القديمة مرة واحدة.
- فرض عزل كامل على كل الاستعلامات.
- دعم أكثر من فرع لنفس الموظف، إلا إذا تقرر ذلك لاحقا.

## 4. أوضاع تشغيل الفروع حسب الشركة

### 4.1 لماذا نحتاج أكثر من وضع؟

لأن نفس النظام موجود على عدة شركات، ولا يصح أن تتحمل شركة صغيرة بدون فروع تعقيد:

- اختيار الفرع في كل شاشة.
- فلتر فروع في الداشبورد.
- صلاحيات فروع.
- رسائل منع بسبب عدم وجود فرع.

وفي نفس الوقت يجب أن تدعم الشركات الأكبر إدارة فروعها وعزل بياناتها.

### 4.2 وضع شركة بدون فروع

هذا هو الوضع الافتراضي الآمن.

السلوك المطلوب:

- لا يظهر رابط "الفروع" في القائمة إلا لمن يملك صلاحيات الإدارة أو عند تفعيل الميزة.
- لا يظهر فلتر الفروع في الداشبورد.
- لا يظهر حقل اختيار الفرع في إنشاء الطلبات أو العقود أو الفواتير.
- لا يتم منع أي عملية بسبب عدم وجود `branch_id`.
- كل التقارير والقوائم تعمل كما كانت قبل إضافة نظام الفروع.
- يمكن إنشاء فرع افتراضي داخلي باسم "الفرع الرئيسي" لكن لا يظهر للمستخدمين كمتطلب يومي.

التعامل مع البيانات:

```text
branch_id يمكن أن يكون null أو يعبأ بالفرع الرئيسي تلقائيا.
```

التوصية:

```text
إنشاء فرع رئيسي افتراضي لكل شركة، لكن عدم إجبار الواجهة على استخدامه إذا كانت ميزة الفروع غير مفعلة.
```

سبب التوصية:

- يسهل الترقية لاحقا إذا قررت الشركة فتح فروع.
- يقلل شروط null في التقارير المستقبلية.
- يحافظ على تجربة بسيطة للشركات التي لا تحتاج الفروع.

### 4.3 وضع شركة لديها فروع

عند تفعيل الفروع للشركة:

- يظهر رابط إدارة الفروع حسب الصلاحيات.
- يظهر فلتر الفروع في الداشبورد لمن لديه صلاحية رؤية كل الفروع.
- يتم ربط الموظفين بفروع.
- يتم ربط السجلات الجديدة بالفرع تلقائيا.
- يمكن عزل القوائم والتقارير حسب الفرع.
- يتم منع موظف فرع من الوصول إلى بيانات فرع آخر بعد تفعيل العزل.

قواعد مهمة:

- الأدمن العام يرى كل الفروع.
- مدير الفرع يرى فرعه.
- موظف الفرع يرى فرعه فقط.
- السجلات القديمة تخضع لخطة ترحيل واضحة.

### 4.4 كيف نحدد وضع الشركة؟

نحتاج إعدادا واضحا يتحكم في الميزة.

اقتراح اسم الإعداد:

```text
branches_enabled
```

مكانه المقترح:

```text
settings
```

أو ضمن نظام الموديولات الموجود إذا كان مناسبا:

```text
system_module_settings
```

القيم:

```text
false = شركة بدون فروع
true  = شركة لديها فروع
```

الأفضل استخدام النظام الموجود لإدارة الموديولات إذا كان يدعم إظهار/إخفاء المزايا حسب الشركة، لأن المشروع لديه:

```text
App\Support\SystemModuleManager
```

لكن حتى لو استخدمنا الموديولات، يجب أن تكون خدمة الفروع قادرة على الإجابة عن سؤال:

```php
branchesEnabled(): bool
```

### 4.5 السلوك البرمجي حسب الوضع

داخل `BranchAccessService` يجب أن يكون أول قرار:

```php
if (! $this->branchesEnabled()) {
    return $query;
}
```

معنى ذلك:

- إذا الفروع غير مفعلة، لا تطبق أي فلترة.
- لا يتم منع الوصول بسبب الفرع.
- لا يتم إظهار حقول الفروع.
- لا يتم إجبار المستخدم على اختيار فرع.

عند إنشاء سجل جديد:

```text
إذا branches_enabled = false:
    branch_id = الفرع الرئيسي إن وجد، أو null

إذا branches_enabled = true:
    branch_id = فرع الموظف أو الفرع المختار حسب الصلاحية
```

### 4.6 الفرق بين الفرع الرئيسي والوضع بدون فروع

وجود فرع رئيسي لا يعني أن الشركة لديها فروع.

الفرع الرئيسي هو سجل تقني وتنظيمي يساعد النظام.

أما تفعيل الفروع فهو قرار تشغيلي يغير الواجهة والصلاحيات والفلترة.

لذلك:

```text
شركة بدون فروع:
    لديها فرع رئيسي داخلي
    branches_enabled = false

شركة لديها فروع:
    لديها فرع رئيسي وفروع أخرى
    branches_enabled = true
```

### 4.7 التوصية المعتمدة: النسخة الموحدة هي الفرع الرئيسي

التوصية الأفضل لهذا المشروع:

```text
اعتبار الوضع الحالي للنظام هو الفرع الرئيسي لكل شركة.
```

بمعنى أن كل شركة تعمل حاليا بدون تقسيم فروع تعتبر كأنها تعمل على:

```text
الفرع الرئيسي
```

لكن لا يتم إظهار هذا الفرع للمستخدمين في الاستخدام اليومي إلا إذا تم تفعيل ميزة الفروع.

هذا يعطينا أفضل توازن:

- لا نكسر سير العمل الحالي.
- لا نفرض اختيار الفرع على الشركات التي لا تملك فروعا.
- نجهز قاعدة البيانات مستقبلا لدعم الفروع.
- يمكن نقل الشركة من وضع "فرع رئيسي فقط" إلى وضع "عدة فروع" بدون إعادة تصميم.

السلوك المقترح:

```text
شركة بدون فروع:
    branches_enabled = false
    default_branch = الفرع الرئيسي
    الواجهة لا تعرض الفروع
    السجلات الجديدة ترتبط بالفرع الرئيسي بصمت أو تترك null حسب مرحلة التنفيذ

شركة لديها فروع:
    branches_enabled = true
    default_branch = الفرع الرئيسي
    تظهر إدارة الفروع والفلترة
    الموظفون والسجلات ترتبط بفروع محددة
```

القرار التنفيذي:

```text
كل شركة يجب أن يكون لديها فرع رئيسي واحد على الأقل.
تفعيل إدارة الفروع شيء منفصل عن وجود الفرع الرئيسي.
```

لذلك لا يكون السؤال البرمجي:

```text
هل يوجد فرع؟
```

بل يكون:

```text
هل ميزة الفروع مفعلة؟
```

وهذا يمنع ظهور تعقيد الفروع في الشركات الصغيرة، مع إبقاء النظام جاهزا للشركات متعددة الفروع.

## 5. تحليل الوضع الحالي

### 5.1 المسارات الحالية

لوحة التحكم الأساسية تعمل من:

```text
routes/admin.php
```

أهم المسارات الحالية:

```text
dashboard
dashboard-pro
dashboard-old
dashboard/employees/{employee}
dashboard/admins
```

المسارات محمية غالبا بـ:

```text
admin
admin.route.permission
```

### 5.2 نظام الصلاحيات

المشروع يستخدم:

- Spatie Permission.
- Middleware باسم `EnsureAdminRoutePermission`.
- مصفوفة صلاحيات داخل `App\Support\AdminRoutePermissionMatrix`.
- مفاتيح صلاحيات داخل `App\Helpers\PermKeys.php`.

أي إضافة للفروع يجب أن تمر عبر نفس منظومة الصلاحيات، وليس عبر تحقق منفصل داخل الواجهات فقط.

### 5.3 المستخدمون الإداريون

نموذج الأدمن:

```text
App\Models\auth\Admin
```

جدول الأدمن:

```text
admins
```

يوجد حاليا:

- `role_id`
- بيانات التواصل.
- حالة المستخدم.
- بيانات الجلسة والنشاط.

المطلوب إضافة `branch_id` اختياريا في البداية.

### 5.4 الداشبورد

الداشبورد يستخدم:

```text
App\Http\Controllers\admin\DashboardController
```

وفيه إحصائيات مباشرة على جداول مثل:

- `orders`
- `maids`
- `users`
- `contracts`
- `rental_contracts`
- `sponsorship_transfers`
- `recruitment_offices`

لذلك فلترة الفروع يجب أن تتم بحذر، لأن الداشبورد يجمع بيانات من عدة مصادر.

## 6. التصميم المقترح للبيانات

### 6.1 جدول الفروع

اسم الجدول:

```text
branches
```

الحقول المقترحة:

```text
id
name
code
city
address
phone
email
manager_id
status
is_main
notes
created_by
updated_by
created_at
updated_at
deleted_at
```

### 6.2 شرح الحقول

| الحقل | النوع | ملاحظات |
|---|---|---|
| `name` | string | اسم الفرع |
| `code` | string nullable unique | كود داخلي للفرع |
| `city` | string nullable | المدينة |
| `address` | text nullable | العنوان |
| `phone` | string nullable | هاتف الفرع |
| `email` | string nullable | بريد الفرع |
| `manager_id` | foreign nullable | مدير الفرع من جدول `admins` |
| `status` | string | `active` أو `inactive` |
| `is_main` | boolean | تحديد الفرع الرئيسي |
| `notes` | text nullable | ملاحظات داخلية |
| `created_by` | foreign nullable | من أنشأ الفرع |
| `updated_by` | foreign nullable | آخر من عدل الفرع |
| `deleted_at` | timestamp nullable | حذف ناعم |

### 6.3 إعداد تفعيل الفروع

نحتاج حفظ حالة تفعيل الفروع لكل شركة.

إذا استخدمنا جدول `settings`:

```text
branches_enabled boolean default false
```

إذا استخدمنا `system_module_settings`:

```text
module_key = branches
enabled = true/false
```

التوصية:

```text
استخدام نظام الموديولات إذا كان الهدف التحكم في إظهار الميزة لكل شركة.
استخدام settings إذا كان المطلوب إعدادا مباشرا وبسيطا داخل إعدادات الشركة.
```

الأهم أن كل أجزاء النظام تستدعي دالة واحدة لتحديد التفعيل، ولا تقرأ الإعداد مباشرة في كل Controller.

### 6.4 ربط الموظفين بالفروع

إضافة حقل إلى جدول:

```text
admins.branch_id
```

الخصائص:

- `nullable`.
- مفتاح أجنبي إلى `branches.id`.
- عند حذف الفرع يكون `nullOnDelete`.

في وضع شركة بدون فروع:

```text
branch_id يمكن تركه فارغا أو ربطه بالفرع الرئيسي.
```

في وضع شركة لديها فروع:

```text
يفضل ربط كل موظف بفرع قبل تفعيل عزل البيانات.
```

### 6.5 الجداول التشغيلية المرشحة للربط

يتم إضافة `branch_id` تدريجيا إلى:

```text
orders
contracts
rental_contracts
sponsorship_transfers
invoices
complaints
support_tickets
maids
```

الأولوية:

1. `orders`
2. `contracts`
3. `rental_contracts`
4. `invoices`
5. `complaints`
6. `support_tickets`
7. `maids`

```text

manager()       belongsTo Admin
```

إضافة علاقات:


إضافة دوال مساعدة:

```text

```

لا توضع قواعد الوصول المعقدة داخل النموذج فقط. الأفضل أن تكون داخل خدمة مركزية.

## 8. خدمة الوصول للفروع

ملف مقترح:

```text
app/Support/BranchAccess.php
```

أو:

```text
app/Services/BranchAccessService.php
```

المهام:

- معرفة هل المستخدم يرى كل الفروع.
- معرفة الفروع المسموحة للمستخدم.
- تطبيق فلتر الفرع على Query Builder.
- تحديد الفرع الافتراضي عند إنشاء سجل جديد.
- منع الوصول إلى فرع غير مصرح.

دوال مقترحة:

```php
public function canViewAllBranches(Admin $admin): bool
public function allowedBranchIds(Admin $admin): array
public function defaultBranchId(?Admin $admin): ?int
public function requestedBranchId(Request $request, Admin $admin): ?int
public function applyToQuery($query, Request $request, Admin $admin, string $column = 'branch_id')
public function assertCanAccess(?Admin $admin, ?int $branchId): void
public function branchesEnabled(): bool
public function shouldShowBranchUi(?Admin $admin): bool
```

### 8.1 قواعد الخدمة حسب وضع الشركة

إذا كانت `branches_enabled = false`:

```text
canViewAllBranches = true من ناحية البيانات
applyToQuery لا يضيف where
assertCanAccess لا يمنع الوصول بسبب branch_id
shouldShowBranchUi = false إلا في صفحة الإعدادات أو لمستخدم إداري
defaultBranchId = الفرع الرئيسي أو null
```

إذا كانت `branches_enabled = true`:

```text
canViewAllBranches يعتمد على الصلاحية
applyToQuery يطبق الفرع للمستخدمين المحدودين
assertCanAccess يمنع الوصول لفرع غير مصرح
shouldShowBranchUi يعتمد على الصلاحية والسياق
defaultBranchId = فرع الموظف أو الفرع الرئيسي للأدمن العام
```

## 9. صلاحيات الفروع

مفاتيح صلاحيات مقترحة:

```text
branches_view
branches_create
branches_edit
branches_delete
branches_manage
branches_view_all
branches_reports
branches_toggle_module
```

### 8.1 معنى الصلاحيات

| الصلاحية | المعنى |
|---|---|
| `branches_view` | عرض قائمة الفروع |
| `branches_create` | إنشاء فرع |
| `branches_edit` | تعديل بيانات فرع |
| `branches_delete` | حذف أو تعطيل فرع |
| `branches_manage` | إدارة كاملة للفروع |
| `branches_view_all` | رؤية كل الفروع وبياناتها |
| `branches_reports` | عرض تقارير الفروع |
| `branches_toggle_module` | تفعيل أو تعطيل ميزة الفروع للشركة |

### 8.2 الربط مع النظام الحالي

يجب تحديث:

```text
App\Helpers\PermKeys.php
App\Support\AdminRoutePermissionMatrix.php
PermissionsController أو مصدر عرض الصلاحيات الحالي
```

بعد الإضافة يتم تشغيل:

```bash
php artisan permissions:prepare-server --role-id=1 --role-name=Administrator --attach-first-admin
php artisan permission:cache-reset
php artisan optimize:clear
```

## 10. المسارات والواجهات

### 10.1 المسارات المقترحة

داخل `routes/admin.php` تحت prefix:

```text
dashboard
```

### 11.1 شاشة الموظفين

```text
dashboard/admins
```

### 11.2 StoreAdminRequest و UpdateAdminRequest

```text
branch_id nullable exists:branches,id
```

### 11.3 AdminController

تحديث:

```text
$postData
```

لإضافة:

```text
branch_id
```

وتحديث DataTables لعرض الفرع والفلترة به.

### 11.4 قواعد الشركات بدون فروع

إذا كانت الشركة لا تستخدم الفروع:

- يمكن ربط كل الموظفين بالفرع الرئيسي داخليا بدون إظهار ذلك.

إذا تم تفعيل الفروع لاحقا:

## 12. سلوك إنشاء السجلات الجديدة

عند إنشاء سجل تشغيلي جديد، إذا لم يرسل المستخدم `branch_id`:

```text
branch_id = فرع الموظف الحالي
```

إذا كان المستخدم لديه صلاحية `branches_view_all` أو `branches_manage`:

- يمكنه اختيار الفرع من القائمة.
- إذا لم يختر فرعا يتم استخدام فرعه الافتراضي أو الفرع الرئيسي.

إذا كان المستخدم موظف فرع:

- لا يظهر له اختيار الفروع.
- يتم تثبيت الفرع تلقائيا.

إذا كانت الفروع غير مفعلة للشركة:

- لا يظهر اختيار الفرع.
- لا يتم منع الحفظ إذا كان `branch_id` فارغا.
- يمكن تعبئة `branch_id` بالفرع الرئيسي بصمت إذا كان ذلك أسهل للتقارير المستقبلية.

### 13.1 المرحلة الأولى

يظهر فلتر "كل الفروع" فقط لمن لديه:

أول مجموعة:

- طلبات التأجير.
- عقود الاستقدام.

```php
$branchAccess->applyToQuery($query, $request, auth('admin')->user());
```

- الداشبورد يعرض نفس الإحصائيات الحالية بدون فلترة فروع.
- لا يظهر فلتر الفروع.
- لا يتم تغيير روابط الكروت أو التقارير.
- لا يتم تطبيق `where branch_id`.

## 14. سياسة عرض البيانات

### 14.1 Administrator / Super Admin

يرى:

- كل الفروع.
- كل البيانات.
- فلتر الفروع.
- تقارير المقارنة بين الفروع.

### 14.2 مدير الفرع

يرى:

- بيانات فرعه.
- موظفي فرعه.
- تقارير فرعه.

لا يرى:

- بيانات الفروع الأخرى.
- إعدادات الفروع الأخرى.

### 14.3 موظف الفرع

يرى:

- سجلات فرعه فقط.
- بياناته ومهامه.

لا يرى:

- فلتر كل الفروع.
- تقارير المقارنة.

### 14.4 شركة بدون فروع

في هذا الوضع لا توجد أدوار تشغيلية خاصة بالفروع.

كل المستخدمين يعملون بنفس منطق الصلاحيات الحالي.

صلاحيات الفروع تستخدم فقط لإدارة تفعيل الميزة أو تجهيزها مستقبلا.

## 15. خطة الترحيل للبيانات القديمة

### 15.1 إنشاء الفرع الرئيسي

بعد تشغيل migration:

```text
إنشاء فرع رئيسي باسم: الفرع الرئيسي
is_main = true
status = active
```

### 15.2 ربط الموظفين الحاليين

الخيار الآمن:

```text
كل admins الحاليين يتم ربطهم بالفرع الرئيسي مبدئيا.
```

ثم تتم مراجعتهم يدويا.

### 15.3 ربط السجلات القديمة

يوجد خياران:

#### الخيار أ: ترك السجلات القديمة بدون فرع

المميزات:

- لا ننسب بيانات قديمة لفرع بشكل خاطئ.

العيوب:

- التقارير حسب الفروع لن تكون مكتملة تاريخيا.

#### الخيار ب: ربط كل القديم بالفرع الرئيسي

المميزات:

- التقارير لا تظهر بيانات "غير محددة".
- أسهل للمحاسبة والمتابعة.

العيوب:

- قد لا يكون تاريخيا دقيقا إذا كانت هناك فروع قديمة.

التوصية:

```text
استخدام الخيار ب إذا لم تكن هناك بيانات فروع قديمة موثوقة.
استخدام الخيار أ إذا كانت الشركة تريد مراجعة تاريخية دقيقة.
```

### 15.4 ترحيل شركة بدون فروع

إذا كانت الشركة لا تملك فروع:

```text
branches_enabled = false
إنشاء فرع رئيسي داخلي
ربط الموظفين بالفرع الرئيسي اختياري
ربط السجلات القديمة بالفرع الرئيسي اختياري
عدم إظهار الفروع في الواجهة اليومية
```

التوصية العملية:

```text
أنشئ الفرع الرئيسي واربط الموظفين به.
اترك الفلترة والواجهة مخفية طالما branches_enabled = false.
```

### 15.5 ترحيل شركة لديها فروع

إذا كانت الشركة لديها فروع:

```text
branches_enabled = true بعد تجهيز البيانات
إنشاء كل الفروع الفعلية
ربط كل موظف بفرعه
تحديد المستخدمين الذين يرون كل الفروع
اختيار سياسة السجلات القديمة
اختبار الداشبورد والقوائم قبل تفعيل العزل الكامل
```

لا يتم تفعيل العزل الكامل قبل:

- وجود فرع نشط واحد على الأقل.
- ربط كل الموظفين التشغيليين بفروع.
- تحديد صلاحيات الأدمن العام.
- مراجعة السجلات القديمة أو اعتماد سياسة افتراضية لها.

## 16. مراحل التنفيذ المقترحة

### المرحلة 0: اعتماد القرار

قبل البرمجة يجب حسم:

- هل الشركة الحالية لديها فروع أم لا؟
- هل ستكون الفروع مفعلة افتراضيا للشركات الجديدة أم معطلة؟
- هل الموظف يتبع فرعا واحدا فقط؟
- هل السجلات القديمة تربط بالفرع الرئيسي أم تترك بدون فرع؟
- من هم المستخدمون الذين يرون كل الفروع؟
- هل يوجد فرع رئيسي واحد فقط؟
- هل المطلوب لاحقا ربط الفواتير محاسبيا بمراكز تكلفة الفروع؟

### المرحلة 1: الأساس

العمل:

- إنشاء جدول `branches`.
- إضافة إعداد `branches_enabled` أو ربطه بنظام الموديولات.
- إنشاء Model.
- إنشاء Seeder للفرع الرئيسي.
- إضافة صلاحيات الفروع.
- تحديث مصفوفة الصلاحيات.

اختبار القبول:

- يمكن تشغيل migrations بدون خطأ.
- يتم إنشاء الفرع الرئيسي.
- تكون الفروع غير مفعلة افتراضيا إلا إذا قررنا عكس ذلك.
- تظهر صلاحيات الفروع في شاشة الصلاحيات.
- Administrator يحصل على الصلاحيات.

### المرحلة 2: CRUD الفروع

العمل:

- إنشاء `BranchController`.
- إنشاء Requests.
- إنشاء views.
- إضافة routes.
- إضافة رابط في القائمة الجانبية حسب الصلاحية.
- إخفاء الرابط في الشركات بدون فروع إلا للمستخدم الإداري.

اختبار القبول:

- يمكن عرض الفروع.
- يمكن إنشاء فرع.
- يمكن تعديل فرع.
- يمكن تعطيل فرع.
- لا يمكن حذف فرع مرتبط بسجلات مهمة.
- شركة بدون فروع لا ترى هذه الشاشة في الاستخدام اليومي.

### المرحلة 3: ربط الموظفين

العمل:

- إضافة `branch_id` إلى `admins`.
- تعديل نموذج Admin.
- تعديل شاشة الموظفين.
- تعديل Store/Update requests.
- إضافة فلتر فرع في قائمة الموظفين.

اختبار القبول:

- يمكن تعيين فرع لموظف.
- يظهر الفرع في جدول الموظفين.
- يمكن فلترة الموظفين حسب الفرع.
- لا يتأثر تسجيل الدخول.

### المرحلة 4: فلتر الداشبورد

العمل:

- إنشاء `BranchAccessService`.
- إضافة فلتر الفروع في الداشبورد.
- تطبيق الفلترة على أهم الإحصائيات فقط.

اختبار القبول:

- الأدمن العام يرى كل الفروع.
- موظف الفرع يرى فرعه فقط.
- إحصائيات الفرع تختلف عند تغيير الفلتر.
- الداشبورد بدون فلتر يعمل كما كان للأدمن العام.
- عند تعطيل الفروع لا يظهر الفلتر ولا تتغير الإحصائيات.

### المرحلة 5: ربط السجلات الجديدة

العمل:

- إضافة `branch_id` تدريجيا إلى الجداول التشغيلية.
- تعبئة الفرع تلقائيا عند الإنشاء.
- إضافة اختيار الفرع فقط لمن لديه صلاحية رؤية كل الفروع.

البداية المقترحة:

```text
orders
contracts
rental_contracts
invoices
```

اختبار القبول:

- أي طلب جديد يأخذ فرع الموظف.
- أي عقد جديد يأخذ فرع الموظف أو الفرع المختار.
- لا يمكن لموظف فرع إنشاء سجل باسم فرع آخر.
- عند تعطيل الفروع لا يفشل إنشاء السجلات بسبب `branch_id`.

### المرحلة 6: عزل القوائم والتقارير

العمل:

- تطبيق فلترة الفروع على القوائم الأساسية.
- تطبيقها على DataTables و Ajax.
- تطبيقها على التصدير إن وجد.

اختبار القبول:

- موظف الفرع لا يرى سجلات فرع آخر.
- الأدمن العام يرى الجميع.
- التصدير يحترم نفس الفلتر.
- الروابط المباشرة لسجل من فرع آخر تمنع الوصول.

### المرحلة 7: تقارير الفروع

العمل:

- صفحة تقرير لكل فرع.
- مقارنة بين الفروع.
- أداء الموظفين حسب الفرع.
- الطلبات والعقود والإيرادات حسب الفرع.

اختبار القبول:

- تقرير الفرع يعرض مؤشرات واضحة.
- تقرير المقارنة يظهر لكل الفروع النشطة.
- النتائج مطابقة للقوائم المفصلة.

## 18. المخاطر وطريقة تقليلها

### خطر: اختفاء بيانات من القوائم

السبب:

تطبيق فلتر فرع مبكر أو بشكل عام.

التقليل:

- لا تستخدم Global Scope في البداية.
- طبق الفلترة شاشة شاشة.
- ابدأ بالداشبورد ثم القوائم المهمة.

### خطر: فرض الفروع على شركة لا تستخدمها

السبب:

إظهار حقول واختيارات الفروع دائما أو جعل `branch_id` مطلوبا.

التقليل:

- استخدام `branches_enabled`.
- إخفاء واجهات الفروع عند تعطيل الميزة.
- جعل `branch_id` اختياريا.
- عدم تطبيق فلترة الفروع إذا كانت الميزة غير مفعلة.

### خطر: تقارير خاطئة

السبب:

السجلات القديمة بدون فرع أو منسوبة خطأ.

التقليل:

- تحديد سياسة واضحة للبيانات القديمة.
- إضافة خيار "غير محدد" مؤقتا.
- مقارنة النتائج قبل وبعد الفلترة.

### خطر: صلاحيات غير ظاهرة

السبب:

عدم تحديث نظام الصلاحيات والكاش.

التقليل:

```bash
php artisan permissions:prepare-server --role-id=1 --role-name=Administrator --attach-first-admin
php artisan permission:cache-reset
php artisan optimize:clear
```

### خطر: كسر DataTables

السبب:

إضافة أعمدة أو فلاتر بدون تعديل Ajax response.

التقليل:

- تعديل الأعمدة في Controller والواجهة معا.
- اختبار Ajax لكل شاشة.

### خطر: مستخدم يصل لرابط مباشر من فرع آخر

السبب:

الفلتر موجود في القائمة فقط وليس في show/edit/update.

التقليل:

- استخدام `assertCanAccess` في show/edit/update/destroy.
- إضافة اختبارات يدوية للروابط المباشرة.

## 19. قواعد التنفيذ الآمن

- كل migration يجب أن يتحقق من وجود العمود قبل إضافته إذا كان المشروع يحتوي migrations كثيرة ومتفرعة.
- كل `branch_id` جديد يكون `nullable` في البداية.
- لا يتم حذف سجلات الفروع فعليا في المرحلة الأولى، فقط تعطيل.
- لا يتم منع الدخول أو إنشاء السجلات بسبب الفرع قبل إكمال ربط الموظفين.
- أي فلترة للفرع يجب أن تحترم صلاحية `branches_view_all`.
- أي فلترة للفرع يجب أن تتوقف بالكامل إذا كانت `branches_enabled = false`.
- واجهات الفروع لا تظهر في الاستخدام اليومي لشركة بدون فروع.
- يجب اختبار الأدمن العام وموظف الفرع على الأقل.

## 21. قائمة اختبار شاملة

### شركة بدون فروع

- `branches_enabled = false`.
- لا يظهر فلتر الفروع في الداشبورد.
- لا يظهر حقل الفرع في إنشاء الطلب أو العقد.
- لا يفشل إنشاء سجل جديد بسبب عدم وجود فرع.
- القوائم تعرض نفس البيانات السابقة.
- الأدمن يستطيع الدخول للنظام بدون ربط صريح بفرع.
- يمكن تفعيل الفروع لاحقا بدون migration جديد.

### الفروع

- إنشاء فرع جديد.
- تعديل فرع.
- تعطيل فرع.
- منع إنشاء كود مكرر.
- منع اختيار مدير غير موجود.
- ظهور الفرع الرئيسي.

### الموظفين

- إنشاء موظف بفرع.
- تعديل فرع موظف.
- عرض فرع الموظف في القائمة.
- فلترة الموظفين حسب الفرع.
- تسجيل دخول الموظف بعد ربطه بالفرع.

### الصلاحيات

- مستخدم بدون `branches_view` لا يرى شاشة الفروع.
- مستخدم لديه `branches_view` يرى القائمة فقط.
- مستخدم لديه `branches_manage` يدير الفروع.
- مستخدم لديه `branches_view_all` يرى كل الفروع.

### الداشبورد

- الأدمن العام يرى "كل الفروع".
- موظف الفرع لا يرى "كل الفروع".
- تغيير الفلتر يغير الإحصائيات.
- لا تظهر أخطاء عند عدم وجود `branch_id` في بعض الجداول.
- عند تعطيل الفروع لا يتم تطبيق أي فلتر فرع.

### السجلات التشغيلية

- الطلب الجديد يأخذ فرع الموظف.
- العقد الجديد يأخذ فرع الموظف.
- الفاتورة الجديدة تأخذ فرع الموظف عند تفعيل المرحلة.
- لا يمكن لموظف فرع تعديل سجل فرع آخر.

### التراجع

- تعطيل فلترة الفروع لا يكسر الشاشات.
- يمكن جعل `branch_id` فارغا بدون فشل.
- الأدمن العام يستطيع رؤية البيانات كلها في أي وقت.

## 22. قرارات مطلوبة قبل بدء البرمجة

يجب اعتماد هذه النقاط قبل التنفيذ:

```text
1. هل الفروع تكون غير مفعلة افتراضيا لكل شركة؟
2. هل الشركة الحالية لديها فروع فعلية؟
3. هل كل موظف يتبع فرعا واحدا فقط؟
4. هل نربط البيانات القديمة بالفرع الرئيسي؟
5. ما أسماء الفروع الحالية إذا وجدت؟
6. من هو مدير كل فرع؟
7. من هم المستخدمون الذين يرون كل الفروع؟
8. هل الفروع مرتبطة محاسبيا بمراكز تكلفة الآن أم لاحقا؟
9. هل نريد تقارير مقارنة الفروع من المرحلة الأولى أم مرحلة لاحقة؟
```

---

## 23. الترتيب العملي المقترح

الترتيب الأفضل للتنفيذ:

```text
1. اعتماد القرارات المطلوبة.
2. تنفيذ إعداد branches_enabled بحيث تكون الفروع اختيارية.
3. تنفيذ جدول الفروع والصلاحيات.
4. تنفيذ شاشة CRUD للفروع.
5. ربط الموظفين بالفروع.
6. إضافة فلتر الداشبورد مع إخفائه عند تعطيل الفروع.
7. ربط الطلبات والعقود الجديدة بالفروع.
8. عزل القوائم المهمة حسب الفرع فقط عند تفعيل الفروع.
9. بناء تقارير الفروع.
10. مراجعة شاملة قبل تفعيل العزل الكامل.
```

هذا الترتيب يقلل المخاطر لأنه يسمح بتشغيل كل مرحلة واختبارها قبل الانتقال للتي بعدها.
